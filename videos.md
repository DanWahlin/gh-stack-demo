# GitHub Stacked PRs Video Series

## Recommendation

Create **three core videos**, each building on the same disposable learner repository. Together they form a clean 25-ish-minute course, but each still works independently.

Do not have the agent rebuild the stack viewers created in Video 2. That would feel repetitive. Instead:

1. Understand and inspect a stack
2. Build and publish one with `gh stack`
3. Use an agent to evolve and maintain that stack

---

## Video 1: Why GitHub Stacked PRs?

**Working title:** *GitHub Stacked PRs: Smaller Reviews Without Slowing Development*  
**Target length:** 6–8 minutes  
**Viewer outcome:** Understand when stacked PRs help, how their branch relationships work, and when not to use them

### Story

#### 0:00 – The uncomfortable choice

- One giant PR keeps development moving but overwhelms reviewers
- Small serial PRs are easier to review but force dependent work to wait

#### 1:15 – Introduce the stack

Use slides 1–3:

- “Getting Started with GitHub Stacked PRs”
- “The Challenge”
- “The High-Level Idea”

Explain:

```text
main
└── tasks/model          → PR targets main
    └── tasks/validation → PR targets tasks/model
        └── tasks/api    → PR targets tasks/validation
```

Emphasize that each PR exposes only the change introduced by that layer.

#### 3:30 – Inspect the real stack

Use the live canonical PRs already documented in the repo:

- [PR #21: model](https://github.com/DanWahlin/learn-github-stacked-prs/pull/21)
- [PR #22: validation](https://github.com/DanWahlin/learn-github-stacked-prs/pull/22)
- [PR #23: API](https://github.com/DanWahlin/learn-github-stacked-prs/pull/23)

The PRs are open, ready for review, and use the intended bases.

Show the **Files changed** tab for each PR and contrast the focused diffs.

#### 6:00 – When to use a stack

Use the README decision model:

- One task feature split into model → validation → API layers: one stack
- Independent authentication and billing changes: separate normal pull requests
- Authentication and billing changes that each have dependent layers: separate stacks

### End state

Create or introduce the private build-mode learner repository. It contains only the scaffold on `main`, ready for Video 2:

```sh
node scripts/create-workshop-copy.mjs \
  YOUR-OWNER/my-stacked-prs-series \
  --build \
  --private
```

## Video 2: Build a Stack with GitHub CLI

**Working title:** *Build and Publish Three Stacked PRs with GitHub CLI*  
**Target length:** 8–10 minutes  
**Viewer outcome:** Build, test, inspect, and submit a real three-layer stack

### Story

#### 0:00 – Start from the learner repository

Use slide 7 briefly for prerequisites:

```sh
gh auth status
gh stack --version
```

The current repo contract is verified against:

- GitHub CLI `2.97.0`
- `gh stack` `0.1.0`

#### 1:00 – Preview the workflow

Use slide 4:

1. Create layers
2. Submit once
3. Review and land

#### 1:45 – Build the bottom layer

```sh
gh stack init --base main tasks/model
```

Add the task model and model test, then:

```sh
npm test
git add src/tasks.js test/tasks.model.test.js
git commit -m "feat: add tested task model"
```

Show the important checkpoint: one passing test and a focused diff.

#### 3:30 – Add validation

```sh
gh stack add tasks/validation
```

Implement validation and its tests. Show four cumulative passing tests.

#### 5:15 – Add the API

```sh
gh stack add tasks/api
```

Implement `POST /tasks`, the start command, and API tests. Show six cumulative passing tests.

#### 7:00 – Inspect and submit

```sh
gh stack view --json
gh stack submit --auto --open
```

Then inspect GitHub and verify:

- Correct base and head for all three PRs
- Focused changed files
- Ready-for-review state
- GitHub stack linkage

The GitHub inspection matters. A successful CLI exit is not enough proof.

### End state

The learner repository now has three open, linked PRs:

```text
main
└── tasks/model
    └── tasks/validation
        └── tasks/api
```

### Production note

Slide 5 is an excellent visual reference, but it is too dense to serve as the entire lesson. Use it as a chapter map, then zoom into the real terminal for each layer.

To keep the runtime below ten minutes, prepare the implementation snippets beforehand. Do not make viewers watch every file being typed.

## Video 3: Manage the Stack with an AI Coding Agent

**Working title:** *Maintain Stacked PRs with the GitHub Copilot App*  
**Target length:** 8–10 minutes  
**Viewer outcome:** Use an agent to change a lower layer safely while keeping the human in control

Use the [GitHub Copilot app](https://github.com/features/ai/github-app) in **local repository mode** so it operates on the same branches and stack metadata created in Video 2.

### Story

#### 0:00 – Why agents need stack boundaries

Explain the failure mode:

> An agent working on the API branch discovers that the model needs to change and puts the model change in the API PR.

That produces the wrong review boundary.

#### 1:00 – Give the agent repository context

Use slide 6 and open the existing learner repository.

Reference `@AGENTS.md`, then start with:

```text
Read AGENTS.md. Do not modify files.

Summarize when to use one stack, which operations require approval,
and what evidence you must return before submitting pull requests.
```

Show that the agent understands:

- Branch order
- Layer responsibilities
- Tests per layer
- Approval before rebase, push, sync, submission, or merge

#### 2:30 – Give it lower-layer feedback

Use the exact workshop scenario:

> Add `priority: 'normal'` to every task and assert the default in the model test.

First ask the agent to plan only.

After approving the plan, have it:

1. Navigate to `tasks/model`
2. Modify the model and its test
3. Run the model tests
4. Commit locally
5. Stop before rewriting or publishing anything

#### 5:30 – Cascade the change

After reviewing the local evidence, approve:

```sh
gh stack rebase --upstack
```

Then move to the top and run the full test suite:

```sh
gh stack top
npm test
gh stack view --json
```

#### 7:00 – Synchronize and verify

After a second explicit approval:

```sh
gh stack push
```

Or use `gh stack sync` if the video is intentionally demonstrating the complete fetch, reconcile, rebase, push, and synchronization workflow.

Finish by inspecting all three live PRs again. Show that:

- The model change remains in the model PR
- Validation and API still build on it
- Every branch remains green
- The stack relationship is intact

### End state

The series finishes with a more complete task API and a realistic demonstration of human-agent collaboration:

- The human approves architecture and remote actions
- The agent implements and verifies
- `AGENTS.md` provides durable repository rules
- `gh stack` preserves the review boundaries

## Optional Video 4: Review, Rebase, and Merge a Stack Safely

**Working title:** *Review, Rebase, and Merge a Stack Safely*  
**Target length:** 6–8 minutes

Make this optional rather than squeezing it into Video 3.

Cover:

- Reviewing from bottom to top
- Responding to review feedback
- `gh stack rebase` conflicts and `--abort`
- Local versus remote stack divergence
- Branch protection and merge queues
- Merging all or part of a stack
- Verifying the final GitHub state

This lets Video 3 stay focused on the AI coding agent workflow instead of becoming a general maintenance command tour.
